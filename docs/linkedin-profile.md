### Post 2 — the thesis (the one that travels)

```
Most companies "adopted AI" by handing out licences and hoping the process catches up.

That is not an AI-native SDLC. That is the old SDLC with a faster keyboard.

An AI-native SDLC changes five things:

1. The unit of work. Not "write this function" but "here is the spec, the constraints and the tests — propose the change." The spec becomes the artifact that matters.

2. Review. A human cannot read ten times the code. So review moves up a level: contracts, invariants, blast radius — plus automated checks that actually block.

3. Tests. If the agent writes the code, the test is the specification. Untested generated code is a liability with good formatting.

4. Security. Not a gate at the end. Access scoped by default, secrets out of the prompt, and every agent action attributable to the human who approved it.

5. Metrics. Cycle time and change-failure rate, not lines of code. If you cannot measure quality, you are not delivering faster — you are borrowing.

The hard part was never the model. It is redesigning the process so the model's speed does not outrun your ability to verify it.

That is the work I am doing at Bay6 right now.
```

### Post 3 — the security counter-argument

```
Speed and security are only a trade-off if security lives at the end of the pipeline.

The pattern I keep seeing: a team adopts agents, delivery accelerates, and the security review becomes the bottleneck. So it gets compressed, then waived, then forgotten. Three quarters later nobody can answer "who approved this change, and what did it touch?"

What I am doing instead:

• Every agent action attributable. Not "the bot did it" — which human approved which plan, with what scope.
• Least privilege by default. The agent gets the access the task needs, not the access the engineer has.
• Secrets never in the prompt. If it can be echoed, it can be exfiltrated.
• Security checks as blocking gates, not dashboards. A control that only reports is a control that gets ignored.

In a regulated industry this is not optional. Audit does not care how fast you shipped.

AI-native delivery and strong security are compatible — but only if the process is designed that way from the start, not bolted on after the velocity arrives.
```

### Post 4 — the point of view

```
Most AI teams ship the demo and call it done.

The demo is the easy part. The hard part is the question a CISO asks in week two: how do you know it still works?

Three things that actually answer it:

1. A golden set you are slightly embarrassed by. Fourteen cases, not four thousand. If you cannot explain every case, you cannot explain a regression.

2. Traces, not logs. Tool selection, arguments, observations, retries. When the agent picks the wrong tool, a log says "error"; a trace says why.

3. Evals wired into the release, not a dashboard nobody opens. If the eval does not block the deploy, it is a report, not a gate.

The model is the least of your problems. The system around it is the product.
```

### Post 5 — the rollout lesson

```
20+ teams adopted our MCP-driven workflows in four weeks. Research and debugging effort dropped about 95%.

What actually made it land — none of it was the model:

1. We shipped a working skill before we shipped a policy. Governance is easy to write and impossible to adopt before anyone has felt the value.

2. Every skill had an owner and a test. A skill with no test is a rumour.

3. We made the failure mode visible. Tool-selection errors and hallucinated arguments went to a dashboard, so teams watched the agent get better instead of taking it on faith.

4. The platform team used the platform. Nothing kills adoption faster than a tool its authors do not use.

Four weeks, seven pilot squads. The unlock was treating agents as software: contracts, tests, owners.
```

### Post 6 — the credibility post

```
30 seconds to 805 milliseconds. On an iPhone. No new hardware.

I ran a vision-language model on-device — Qwen2-VL-2B through llama.cpp and a GGUF quantization ladder — and the first version took 30s to produce a token. Unusable.

What fixed it, in order of impact:

• Resolution, not model size. The image encoder was doing far more work than the task needed.
• The quantization ladder, measured. 270 benchmark runs, not vibes.
• Per-stage decomposition of time-to-first-token. Once you can see where the milliseconds go, the fix is usually obvious.

The lesson generalises to every AI product I have built since: the biggest wins are almost never "use a better model". They are architecture and input shaping.

Write-up: https://xpressabhi.github.io/blog/on-device-vlm-iphone.html
```
